# Manual Developer-Patch Examples (Defects4J)

**Scope:** These are worked examples for the paper's **manual developer-patch inspection and atomic operator mapping**. They are not RQ5 outputs, and no RQ5 experiment is run by this package.

## Included examples

| Bug | Changed source file | Existing source annotation | Atomic mapping illustrated |
|---|---|---|---|
| Cli-3 | `TypeHandler.java` | `MCR[2], CI[36]` | Method-call replacement + condition insertion |
| Cli-4 | `Parser.java` | `SM[30]` | String/message modification |
| Cli-5 | `Util.java` | `CI[36], MRV[145]` | Null-guard condition + return behavior |
| Cli-8 | `HelpFormatter.java` | `CR[6]` | Constant replacement |

The full operator names follow the 33-family taxonomy in the supplied study audit workbook:
- `CI`: Condition Insertion / Removal
- `MCR`: Method Call Replacement / Removal
- `MRV`: Modification of Return Value
- `SM`: String Modification
- `CR`: Constant Replacement

## Patch provenance and direction

The patch files in `patches/` are **source-only developer-direction patches (buggy → fixed)**. They were prepared by reversing the corresponding official Defects4J `*.src.patch` files, which Defects4J uses in the opposite direction (fixed → buggy) when reconstructing a buggy checkout. The reverse direction is the one needed for inspecting the developer's repair.

Official Defects4J source patches:
- [Cli-3](https://raw.githubusercontent.com/rjust/defects4j/master/framework/projects/Cli/patches/3.src.patch)
- [Cli-4](https://raw.githubusercontent.com/rjust/defects4j/master/framework/projects/Cli/patches/4.src.patch)
- [Cli-5](https://raw.githubusercontent.com/rjust/defects4j/master/framework/projects/Cli/patches/5.src.patch)
- [Cli-8](https://raw.githubusercontent.com/rjust/defects4j/master/framework/projects/Cli/patches/8.src.patch)

The upstream buggy/fixed revision IDs are recorded in `metadata/patch_manifest.csv` from Defects4J's [`framework/projects/Cli/active-bugs.csv`](https://raw.githubusercontent.com/rjust/defects4j/master/framework/projects/Cli/active-bugs.csv).

**Important hash distinction:** The upstream revision IDs in the manifest are not the same thing as the local Git commit hashes generated by a Defects4J checkout. Defects4J creates local `D4J_Cli_<bug>_BUGGY_VERSION` and `..._FIXED_VERSION` tags in the checkout. Run `reproduce_local_git_diff.sh` to record those local tag hashes and generate the full local `git diff` patches.

## Reproduce the exact local diffs

On the research server:

```bash
export PATH="/home1/furqan/tools_and_libs/defects4j/framework/bin:$PATH"

bash reproduce_local_git_diff.sh
```

Or specify an output root:

```bash
bash reproduce_local_git_diff.sh "$HOME/manual_mapping/defects4j"
```

The script checks out each buggy version once, verifies that both local Defects4J tags exist, resolves their commit hashes, and writes:

```text
local_git_diff/
├── Cli-3/
│   ├── Cli-3.full.patch
│   ├── changed_files.txt
│   ├── diff_stat.txt
│   └── metadata.txt
├── Cli-4/
├── Cli-5/
└── Cli-8/
```

The `.full.patch` files contain all changes between the local buggy and fixed tags, including test changes. The `patches/Cli-*.patch` examples are source-only and are the appropriate artifacts for the operator mapping shown here.

## Atomic-decomposition records

Each example has a corresponding file under `atomic_decomposition/`. It records:
1. The changed source file.
2. The buggy-to-fixed semantic change.
3. The atomic edit(s).
4. The exact canonical operator code and Table 3 description.
5. A short rationale for the classification.

Do not treat the source annotation alone as proof. For a final manual mapping, retain the original patch, the local revision hashes, and the human-reviewed atomic-decomposition record together.

## Validation performed on the included patch files

Each included `.patch` file was parsed by `git apply --stat` to check unified-diff syntax. This is a format check only; it is not a substitute for applying the patch to the exact benchmark checkout or running the Defects4J tests.
